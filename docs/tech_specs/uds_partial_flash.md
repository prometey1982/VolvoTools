# ТЗ: частичная прошивка UDS — выбор блоков для стирания и записи (`calculateBlocksToWrite`)

## 1. Цель

Не стирать и не писать весь flash-образ, если часть блоков на ЭБУ уже совпадает с прошиваемым VBF. Контрольные суммы блоков считает сам ЭБУ (routine `0x31 01 FF 01`), по несовпавшим блокам строится **план**: какие erase-диапазоны стереть и какие блоки записать. План строится **итеративно**: стирание диапазона уничтожает лежащие в нём блоки, их приходится дописывать, а это может потребовать стирания новых диапазонов. Итерации идут до стабилизации наборов (неподвижная точка), после чего план применяется целиком.

Реализация: `Flasher/src/UDSFlasher.cpp` (`UDSFlasherImpl::calculateBlocksToWrite()` + частные помощники), новое состояние HFSM `CheckFlash` между `StartBootloader` и `EraseFlash`.

Публичный API `UDSFlasher` / `UDSProtocolCommonSteps` не меняется.

## 2. Модель данных и термины

| Термин | Тип / источник | Смысл |
|---|---|---|
| **Блок прошивки** (chunk) | `common::VBFChunk{writeOffset, data, crc}` — `_config.flash.chunks` | Единица записи: `transferChunk` делает на блок `0x34` → `0x36`×N → `0x37` |
| **Стираемый диапазон** (erase candidate) | `common::DataBlock{startAddr, length}` — `_eraseCandidates` | Атомарная единица стирания: `eraseChunk` шлёт `0x31 01 FF 00` с (адрес, длина) |
| **CRC блока** | `chunk.crc` (`uint32_t`, младшие 16 бит) | Ожидаемая CRC16 блока. Для `.vbf` читается из файла, для `.hex`/binary считается `common::crc16()` |
| **CRC на ЭБУ** | routine `0x31 01 FF 01`, ответ `0x71 01 FF 01 10 <crc_hi> <crc_lo>` | То же значение, которое `transferChunk` отправляет в TransferExit `0x37` |
| `W[i]` | `std::vector<bool> writeNeeded` | Блок `i` нужно писать |
| `S[j]` | `std::vector<bool> eraseNeeded` | Диапазон `j` нужно стереть |

**Источник стираемых диапазонов** (`buildEraseCandidates`):

1. `VBFHeader::eraseBlocks`, если список не пуст (реальные Volvo VBF, а также образы, собранные `VBFUtil.cpp` для ME7/ME9P1/ME9P3/DEMGen2/DEMGen3/DensoP3Restyling);
2. иначе — **1:1 с блоками прошивки** по адресу и длине: предполагается, что гранулярность стирания совпадает с размером блока (DensoP3, AW55, TF80, любой `.hex`/binary, где `eraseBlocks` пуст).

Диапазоны — **атомарные**: дробить их нельзя (гранулярность сектора на стороне ЭБУ неизвестна). Диапазоны сравниваются как полуинтервалы `[startAddr, startAddr + length)` в `uint64_t` (`BlockRange`), поэтому «встык» (конец одного = начало другого) пересечением не считается.

Соотношение блоков и диапазонов в реальных образах разное:

| Образ | Соотношение | Пример |
|---|---|---|
| ME7, ME9P1, ME9P3, DensoP3Restyling | 1:1 | 4 блока ↔ 4 диапазона |
| DEMGen2 | 1:N | блок `0x10000+0x30000` перекрывает 3 диапазона |
| DEMGen3 | 1:N | блок `0x18000+0x38000` перекрывает 4 диапазона |
| DensoP3, AW55, TF80, `.hex` | диапазоны выводятся из блоков | 1:1 по построению |

## 3. Инварианты плана

Итоговые наборы `W` и `S` обязаны удовлетворять:

1. **Всё, что пишем, лежит в стёртом.** Если `W[i]`, то для каждого диапазона `j`, пересекающегося с блоком `i`, выполнено `S[j]` (иначе запись в нестёртую память).
2. **Всё стёртое, покрытое блоками, перезаписывается.** Если `S[j]`, то для каждого блока `i`, пересекающегося с диапазоном `j`, выполнено `W[i]` (иначе данные уничтожены и не восстановлены).
3. **Непокрытые участки** стёртого диапазона (не покрытые ни одним блоком) восстановить нечем — это допустимая ситуация, она только сообщается в лог (см. §6).
4. **Минимальность и детерминизм.** Наборы — наименьшая неподвижная точка: они не растут без необходимости и не зависят от порядка обхода.

Компактная формулировка инвариантов 1–2: для любой пересекающейся пары «блок `i` × диапазон `j`» верно `W[i] == S[j]`.

## 4. Алгоритм

```
calculateBlocksToWrite():
    stateUpdater(CheckFlash)

    если частичный режим неприменим (нет диапазонов / диапазон нулевой длины):
        applyFullRewrite()          # стереть все диапазоны, писать все блоки
        return

    # Шаг 1. Опрос ЭБУ — единственный источник истины о том, что уже совпадает.
    для каждого блока i:
        clearRx()
        ok, crc = getChunkCRC16(block_i)                 # 0x31 01 FF 01
        W[i] = !ok || (crc != (chunk_i.crc & 0xFFFF))    # не спросили — считаем «отличается»
        лог DEBUG по блоку, счётчики differing / failed
    лог INFO: «flash check finished: N blocks, K differ, F crc requests failed»
    S = ∅

    # Шаг 2. Замыкание до неподвижной точки (не более n + m + 1 итераций).
    repeat:
        changed = false
        # 2a. Вперёд: записываемый блок требует стереть все перекрытые им диапазоны.
        для i, где W[i]:
            для j, где пересекается(block_i, candidate_j):
                если !S[j]: S[j] = true; changed = true
        # 2b. Назад: всё, что попало в стираемый диапазон, будет уничтожено — надо записать.
        для j, где S[j]:
            для i, где пересекается(block_i, candidate_j):
                если !W[i]: W[i] = true; changed = true
    пока changed

    # Шаг 3. Проверка инвариантов (§3): для любой пересекающейся пары W[i] == S[j].
    #        Нарушение → ERROR + applyFullRewrite().

    # Шаг 4. Применение.
    applyPlan(W, S)
```

**Сходимость.** Оба правила только добавляют элементы, решётка конечна (`n + m` бит), каждая итерация строго увеличивает `|W| + |S|` → не более `n + m` итераций, после чего `changed == false`. Предел — наименьшая неподвижная точка монотонного оператора, поэтому результат детерминирован и не зависит от порядка обхода. Сложность O((n+m)·n·m); на реальных образах `n, m ≤ 30` — доли микросекунды.

**Применение плана** (`applyPlan`):

- `_blocksToWrite = W`;
- `_blocksToErase` — только выбранные `S[j]`, **по возрастанию адреса**; по одному запросу стирания на диапазон, смежные диапазоны **не сливаются** (решение по железу: сливать нельзя);
- лог INFO: `flash plan: erase X of Y ranges (B bytes), write K of N blocks (B bytes)`;
- отчёт о непокрытых участках (`logUncoveredAreas`, §6);
- пересчёт максимума прогресса: `SBL + Σ размеров блоков с W[i] == true` (`maxProgressUpdater`) — см. §5.

**Откат к полной перезаписи** (`applyFullRewrite`: все `W[i] = true`, `_blocksToErase = _eraseCandidates`, максимум прогресса как раньше) выполняется, если:

| Условие | Лог |
|---|---|
| `_eraseCandidates` пуст | `WARNING no erase ranges declared, writing everything` |
| у диапазона `length == 0` (синтаксис `erase = 0x...;` в VBF) | `WARNING erase range 0x... has zero length, writing everything` |
| замыкание не сошлось за `n + m + 1` итераций | `ERROR flash plan did not converge in N iterations` |
| нарушен инвариант §3 | `ERROR flash plan invariant is broken for block 0x... and erase range 0x...` |

**Безопасный дефолт.** `_blocksToWrite` инициализируется «все `true`», `_blocksToErase` — всеми кандидатами (конструктор `UDSFlasherImpl`). Алгоритм только **сужает** наборы. Поэтому любой сбой — исключение, неподдерживаемая CRC-рутина, отказ от частичного режима — оставляет поведение «стереть и записать всё», а не полупрошитый ЭБУ.

## 5. Интеграция

### 5.1. Место в HFSM

```
KeepAlive → FallAsleep → StartProgrammingSession → Authorize → LoadBootloader
          → StartBootloader → CheckFlash → EraseFlash → WriteFlash → CheckValidApplication
```

`CheckFlash` (`UDSFlasherImpl::calculateBlocksToWrite()`) стоит **после** `StartBootloader` и **до** `EraseFlash`: CRC-рутина `0xFF01` предоставляется запущенным SBL, а опрос обязан пройти до первого стирания. `FlasherState::CheckFlash` выводится CLI как `Checking flash`.

### 5.2. Потребители плана

| Метод | Использование плана |
|---|---|
| `eraseFlash()` | Стирает только `_blocksToErase` (в лог DEBUG — адрес и длина каждого диапазона) |
| `writeFlash()` | Пропускает блоки с `_blocksToWrite[i] == false` (в лог DEBUG — `flash block 0x... is up to date, skip writing`) |
| `getMaximumProgress()` | Остаётся исходным (`SBL + весь flash`) — это значение выставляется до запуска FSM |

### 5.3. Прогресс

Максимум прогресса пересчитывается **после** проверки: `setMaximumProgress(SBL + объём выбранных к записи блоков)`. Причина: писать будем меньше, а `incCurrentProgress` вызывается только на записанные байты, поэтому 100% достигается ровно (раньше при частичной записи полоса «не доезжала» до конца). При «ничего не отличается» максимум равен объёму SBL, то есть прогресс сразу 100%.

### 5.4. Опрос CRC (`UDSProtocolCommonSteps::getChunkCRC16`)

- перед запросом вызывается `channel.clearRx()` — ответ на предыдущий запрос не должен приниматься за ответ на текущий (от результата зависит, писать блок или пропустить);
- **формат ответа**: `71 01 <routineId> <ширина контрольной суммы в битах> <данные>`, то есть `71 01 FF 01 10 <crc_hi> <crc_lo>` для CRC16: пятый байт `0x10` = 16 бит, дальше сама CRC (big-endian). У рутины стирания `0xFF00` на этом месте `0x00` — ноль бит данных (`eraseChunk` ждёт ответ `{0x71, 0x01, 0xff, 0x00, 0x00}`), что подтверждает семантику поля. Ранее код читал `response[4..5]`, то есть ширину и **старший** байт CRC: на железе (Denso P3 restyling) это давало «отличаются все 24 блока» вместо реальных двух, потому что CRC сдвигалась на байт;
- проверяются `response.size() >= 7` и весь префикс `71 01 FF 01 10`; при несовпадении — `ERROR` с дампом ответа и `false` (блок уходит в запись). Ширина `!= 0x10` тоже отвергается: при CRC другой разрядности «два байта после поля» не являются CRC16, а неверная CRC может привести к пропуску реально отличающегося блока;
- распарсенное значение и сырой ответ пишутся в `DEBUG` (`getChunkCRC16 response: ... -> crc 0x...`);
- таймаут ответа — 1000 мс (как было). Негативный ответ ЭБУ приводит к `false` → блок уходит в запись, то есть ошибка опроса трактуется консервативно. `0x78` (`requestCorrectlyReceived-ResponsePending`) ошибкой не считается: `UDSRequest::process` в этом случае продолжает ждать финальный ответ — актуально для CRC по большим диапазонам.

## 6. Краевые случаи

| Ситуация | Поведение |
|---|---|
| Все блоки совпадают | `S = ∅`, `W = ∅` → не стираем и не пишем, сразу `checkValidApplication`, прогресс 100% |
| Блок отличается, перекрывает несколько диапазонов | стираются **все** перекрытые диапазоны (DEMGen2/Gen3) |
| Диапазон перекрывает несколько блоков, часть из них совпадала | совпадавшие блоки дописываются (инвариант 2) — это и есть «дополнение записываемых блоков» |
| Дописанный блок сам перекрывает новый диапазон | новый диапазон добавляется в стирание (следующая итерация) — это и есть «снова расширить диапазон удаляемых» |
| Диапазон не перекрыт ни одним блоком | никогда не выбирается → не стирается (безопаснее прежнего поведения, где стирались все объявленные диапазоны) |
| Блок не перекрыт ни одним диапазоном | пишется без стирания (если отличается); отдельного лога нет — диапазонов для него просто нет |
| Стираемый диапазон покрыт блоками частично | `INFO erase range 0x... is not covered by flash blocks: [0x..., 0x...) will stay erased`. Это **правильное** поведение: например, последний блок Denso restyling (`0x1E0000+0x1FF00`) короче своего диапазона (`0x1E0000+0x20000`) — писать хвост `0x1FFF00..0x200000` нельзя, блок заваливается |
| Опрос CRC по блоку не удался | блок считается отличающимся и уходит в запись |
| Опрос CRC не удался по всем блокам (например, SBL без рутины `0xFF01`) | в запись уходят все блоки → стирание всех перекрытых диапазонов → полная перезапись, как до введения механики |
| В образе нет блоков | `W` пуст, `S` пуст → ничего не делаем |

## 7. Логирование

| Уровень | Сообщение | Смысл |
|---|---|---|
| `DEBUG` | `flash block 0x... - crc 0x... matches, skip` | блок совпал |
| `DEBUG` | `flash block 0x... - crc 0x... != expected 0x..., will write` | блок отличается |
| `DEBUG` | `flash block 0x... - crc request failed, will write` | опрос не удался |
| `DEBUG` | `getChunkCRC16 response: ... -> crc 0x...` | сырой ответ рутины CRC и распарсенное значение (модуль `common`) |
| `INFO` | `flash check finished: N blocks, K differ, F crc requests failed` | итог опроса |
| `WARNING` | `all N blocks differ from the image on the ECU, full erase and write will be done` | отличаются все блоки: либо ЭБУ действительно пуст, либо рутина CRC отвечает не тем, что мы ждём |
| `INFO` | `flash plan: erase X of Y ranges (B bytes), write K of N blocks (B bytes)` | итоговый план |
| `INFO` | `erase range 0x... is not covered by flash blocks: [0x..., 0x...) will stay erased` | непокрытый участок |
| `DEBUG` | `erase range 0x..., size N` / `flash block 0x... is up to date, skip writing` | исполнение плана |
| `WARNING` | отсутствие/нулевая длина диапазонов | частичный режим отключён |
| `ERROR` | несошедшийся план, нарушение инварианта, неожиданный ответ `getChunkCRC16` | ошибки, ведущие к полной перезаписи |

Модуль логирования — `"flasher"` (`UDSFlasher.cpp`) и `"common"` (`UDSProtocolCommonSteps.cpp`); `DEBUG` включается `VOLVOLOG_DEBUG=flasher,common`.

## 8. Примеры

**1:1 (ME9P3, 4 блока ↔ 4 диапазона).** Отличается только первый: итерация 1 — `2a` кладёт диапазон 0 в `S`; `2b` ничего не добавляет (блок 0 уже в `W`); итерация 2 — изменений нет. План: стереть 1 из 4, писать 1 из 4.

**1:N (DEMGen2: блок `0x10000+0x30000` ↔ диапазоны `0x10000`, `0x20000`, `0x30000` по `0x10000`).** Отличается этот блок: `2a` добавляет все три диапазона, `2b` — сам блок. Второй блок (`0x6000+0x2000`) не затронут: его диапазон не выбран, стирания там нет.

**Стирание задело совпадавший блок.** Диапазон `0x10000+0x20000` покрывает блоки A (`0x10000+0x10000`, отличается) и B (`0x20000+0x10000`, совпадает). Итерация 1: `2a` — диапазон выбран по A; `2b` — B перекрывается стираемым диапазоном → B добавлен в запись; итерация 2 — изменений нет. План: стереть диапазон, писать A и B.

**Пересечение границы диапазонов.** Блок C (`0x1F000+0x2000`) отличается и перекрывает диапазоны `0x10000+0x10000` и `0x20000+0x10000`; блок B (`0x20000+0x1000`) совпадает. `2a` добавляет оба диапазона, `2b` добавляет B. Если бы B перекрывал ещё и третий диапазон, тот добавился бы следующей итерацией.

## 10. Критерии готовности

1. ✓ План стирания/записи строится итеративно до неподвижной точки; при сходимости выполняются инварианты §3.
2. ✓ Совпадающие блоки не пишутся; диапазоны без отличающихся блоков не стираются.
3. ✓ Блоки, уничтожаемые стиранием, дописываются; вызванные этим стирания добавляются в план.
4. ✓ Порядок состояний: `CheckFlash` после `StartBootloader`, до `EraseFlash`.
5. ✓ Максимум прогресса пересчитывается после проверки; при отсутствии изменений прогресс не «висит» на нуле.
6. ✓ Любой сбой (нет диапазонов, нулевая длина, несошедшийся план, нарушение инварианта, отказ опроса) деградирует к полной перезаписи с записью причины в лог.
7. ✓ Смежные диапазоны не сливаются, порядок стирания — по возрастанию адреса.
8. ✓ Непокрытые участки стираемых диапазонов не считаются ошибкой (Denso restyling) и сообщаются на уровне `INFO`.
9. ✓ Публичный API `UDSFlasher`/`UDSProtocolCommonSteps` не изменён.
10. ✓ Сборка без ошибок (Release, x64; x86 — по CI).

## 11. Ограничения и что сознательно не делается

1. **Гранулярность стирания не дробится.** Если объявленный диапазон больше физического сектора или покрывает несколько блоков, стирается он целиком: границы секторов на стороне ЭБУ неизвестны, а «лишний» сектор мог бы снести блок, который решено не писать.
2. **Непокрытые участки не восстанавливаются** (чтение/сохранение/возврат не делается) — в поддерживаемых образах такие участки либо отсутствуют, либо это ожидаемый хвост последнего диапазона Denso restyling.
3. **Диапазон нулевой длины** (одиночный адрес `erase = 0x...;` в VBF, грамматика `VBFParser.cpp`) не поддерживается частичным режимом: неизвестна длина — непонятно, что именно уничтожит стирание.
4. **CRC сверяется только по блокам прошивки.** SBL грузится и стартует до проверки, его блоки не проверяются и не пропускаются.
5. **Таймаут опроса** — 1000 мс (значение по умолчанию `UDSRequest::process`). Если CRC по большому диапазону на конкретном ЭБУ считается дольше, блок просто уйдёт в запись (безопасно, но лишняя работа); при необходимости таймаут выносится в параметр.
6. **Замыкание не покрыто юнит-тестами**: логика живёт внутри `UDSFlasherImpl` в `.cpp` (`Flasher/test` не имеет доступа). При необходимости выносится в чистую функцию от диапазонов и результатов опроса.
